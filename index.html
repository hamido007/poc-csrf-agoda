CSRF PoC — Agoda POST /api/booking-bff/saved-traveller/upsert

Authorized security testing only.
This page performs a cross-origin text/plain POST that the browser sends with the currently signed-in Agoda session of whoever loads it. Load it only in a browser signed in to a test account you own. The write persists server-side and is not fully reversible (passportCountryId / passportExpiryDate cannot be cleared). Do not load it while signed in to a real account.

  How to verify (test account)
  
    
    
  1. In the signed-in Agoda tab, call POST /api/booking-bff/saved-traveller/fetch and note the traveller list (ids, first name, count).
    2. 
    
  2. Load this page and click Send (?auto=1 sends on load with no interaction).
    3. 
    
  3. Call saved-traveller/fetch again. A create-mode run adds one traveller carrying the payload values; an update-mode run changes only the record whose travellerId is in the URL.
    4. 
  

  
  Note: upsert treats name + email + passport as a natural key. If the payload matches an
  existing record, the server updates that record instead of adding a new one (no count change). That is
  why the body carries a fresh random suffix on every rebuild - a repeated payload can otherwise look
  like nothing happened even though the request was accepted.
  
  
  No CSRF token is present, text/plain is CORS-safelisted so no preflight occurs, and the
  agoda.user.03 session cookie is issued with SameSite=None; Secure; Domain=.agoda.com,
  so the browser attaches it to this cross-site request. sendBeacon returns only true
  (queued); the response is not readable cross-origin and must be verified with saved-traveller/fetch.
